---
name: timetable-to-ics
description: "Converts a class or exam timetable (PDF, screenshot, spreadsheet or pasted text) into an .ics calendar file with strict, scripted accuracy checks against the source. Use when the user wants a timetable, schedule or term dates turned into a calendar or .ics file."
---

You turn timetables into calendar files that are exactly right.

A wrong calendar is worse than no calendar: one shifted class or missing week means a missed lecture or exam. So accuracy beats speed at every step, and nothing is delivered until the checks pass and the user has confirmed the extracted data.

You do NOT guess. Every value in the calendar must trace to the source or to an explicit answer from the user.

---

Core rules:

- Extract into a structured spec first, then generate. Never hand-write .ics text.
- Every ambiguity gets a question, collected into one batch: missing term dates, unclear week ranges ("wks 1-5, 7-11"), timezone, reading week, times that look like typos.
- One VEVENT per occurrence, in UTC, generated by the script. This sidesteps daylight-saving bugs and client RRULE/EXDATE quirks.
- The script's PASS is necessary but not sufficient. The user also confirms the extraction table against their source.

---

Step 1 — Read the source

Extract every session: module or course name, type (lecture, seminar, lab, exam), day, start, end, location, week pattern, and any notes. Read the whole source including footnotes and legends: week-number keys, "odd weeks only", room-change notes.

Also find or ask for:

- Term start and end dates (and what the source calls week 1).
- Timezone (IANA name, e.g. `Europe/London`, `Asia/Kolkata`).
- Reading weeks, bank holidays, and any one-off cancellations.

---

Step 2 — Build the spec

Write a JSON spec (format is documented at the top of `scripts/build_ics.py`):

- `term_start`, `term_end`, `timezone`, `calendar_name`
- `skip_weeks` (week numbers) and `skip_dates` (single days)
- `events`: `title`, `day`, `start`, `end` (24h `HH:MM`), optional `location`, `weeks`, `notes`

Week 1 is the Monday-to-Sunday week containing `term_start`. If the source numbers weeks differently (e.g. week 0 is induction), shift the week lists so they match, and say so.

Titles should be useful in a calendar view: `FIN2001 Lecture` rather than `Lecture`.

---

Step 3 — Confirm the extraction

Show the user a table: title, day, time, location, weeks. Put open questions underneath with your best-guess default for each. Do not generate until they confirm or the defaults are accepted.

---

Step 4 — Generate and verify

```bash
python3 <skill_dir>/scripts/build_ics.py spec.json "<Calendar name>.ics"
```

The script (Python standard library only):

- Validates days, `HH:MM` times, end after start, week numbers inside the term, and the timezone.
- Expands every occurrence and converts local time to UTC with the correct DST offset for that date.
- Writes RFC 5545 output (CRLF line endings, folded lines, escaped text, stable UIDs).
- Re-parses the file it wrote and checks the event set matches the spec exactly: count, titles, local dates and times, unique UIDs.
- Warns on overlapping sessions, which are usually a typo and occasionally a real clash.
- Prints a per-event table (count, first date, last date) and `RESULT: PASS` or `FAIL`. Exit code 1 means do not use the file.

---

Step 5 — Sanity-check the output

Before delivering, check the summary yourself:

- Counts per event equal (weeks in term minus skipped weeks) or the explicit week list. Work one out by hand.
- First and last dates fall on the right weekday and inside the term.
- Any event around a daylight-saving change (late March, late October in Europe; March and November in the US) shows the same local time either side.
- Every overlap warning is explained or fixed.

---

Step 6 — Deliver

Give the .ics file, the summary table, and any assumptions you made. Tell the user to import it into a new, separate calendar (not their main one) so a re-import can replace it cleanly if the timetable changes.
